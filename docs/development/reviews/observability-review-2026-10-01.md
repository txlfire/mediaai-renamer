## 3. 缺陷详情

本节原始证据及后续日期检查点均保留，不把537/541等历史测试数当当前终态；最新命令与日志只维护在实施计划第6节。

### R27：日志“不能影响业务”的保护不完整

- 位置：`backend/app/service/operation_log_service.py:174`、`:181`、`:211`。
- 原因：detail 的脱敏/JSON 序列化、大小计算和数据库连接在 try 之前；不可序列化对象、目录/数据库连接故障仍抛给业务。except 内 rollback 自身失败也没有独立保护。
- 证据：detail 包含 object() 抛 TypeError；模拟连接 OperationalError 原样抛出，未降级为 None。
- 影响：辅助日志故障可能中断扫描/改名；函数注释提供了比实现更强的保证。
- 建议：保护整个准备与写入流程，连接初始化失败无需 rollback，清理/关闭失败不覆盖主异常；降级记录包含任务类型、ID、阶段和受控诊断。不能无条件吞掉调用方共享连接中的事务故障。
- 验收：连接、序列化、插入、回滚、清理、关闭各阶段故障均有明确边界；测试业务是否继续与共享事务是否仍有效。

### R28：审计错误发生在业务提交之后

- 位置：`backend/app/api/users.py:76`、`:88`；媒体源/设置/改名 API 同类调用顺序。
- 原因：业务服务使用自己的连接提交，路由随后独立调用 record_audit_event；审计服务没有降级或可靠补写机制。
- 证据：直接调用创建用户路由，注入审计写入异常后调用抛错，但 list_users 已包含新用户。应用当前没有统一自定义异常转换，此异常经路由会成为服务端错误。
- 影响：前端认为失败并重试，可能导致重复动作；已成功的敏感操作缺少审计。该问题与 R17 的“记录了错误成功状态”不同。
- 建议：可共享数据库事务的纯数据库业务，把操作和审计意图一起提交；文件/外部动作使用可靠审计意图和补写机制。审计失败的产品政策应区分执行前拒绝与执行后已生效，不能假装回滚，也不能简单静默忽略全部审计失败。
- 验收：用户/设置/媒体源、文件动作分别注入审计故障，客户端结果与真实状态一致；补写可追踪、幂等，错误提示不会引导盲目重复执行。

- 2026-10-05修复检查点：纯数据库维护已覆盖用户/设置/媒体源/元数据Provider/回滚计划创建与干跑/默认管理员初始化；远端恢复API复用持久化文件审计意图，最终失败返回真实结果和pending提示，补写不MOVE。最新537项（527通过、10NAS跳过）155.371秒，见当日续做记录第5-8节。仍验证中：外部提交决定待D/F01同事务改造；原重命名/回滚缺结果补写的并发归属要追加故障注入；远端缺请求结果一律pending需人工核对，不能称全部崩溃窗口自动恢复。

- 后续第9-10节覆盖上述待补项：外部提交决定已与审计同事务，标明未实际提交；重命名/回滚请求与维护交错红灯复现后修正，缺结果一律pending、拒绝请求failed不归为旧业务成功。最终541项（531通过、10NAS跳过）147.420秒，编码/diff通过。R28保持验证中：进程崩溃结果未保存要人工核对，审计容量/真实平台仍待；F01真实外发是下一实施单元，不因决定审计正确而关闭。

### R29：扫描清理异常触发已释放事务回滚

- 位置：`backend/app/service/scan_service.py:706-713`。
- 原因：RELEASE SAVEPOINT、commit 与 cleanup_operation_logs 在同一 try；清理失败进入扫描失败分支，尝试 ROLLBACK TO 已释放的 savepoint。
- 证据：注入 synthetic cleanup failure，最终抛 no such savepoint；查询数据库扫描状态 completed、媒体结果已存在。
- 影响：真实扫描成功却报数据库错误；主原因被遮蔽；用户可能重复扫描。与 R03 实时事务不可见问题独立。
- 建议：分开业务事务阶段与提交后维护阶段；清理失败记录维护告警、不更改已提交扫描结果。失败处理确认事务阶段，不再操作不存在的 savepoint。
- 验收：清理失败仍返回实际扫描结果，维护告警可查；提交之前的业务失败仍正确回滚并记录原始原因。

### R30：TMDB 详情降级没有任何诊断

- 位置：`backend/app/service/tmdb_client.py:97-108`；`metadata_provider_registry.py:78` 也静默处理主认证回退。
- 原因：详情请求捕获所有 Exception 后返回空对象，不保存 provider_id、错误分类、警告或异常栈。
- 证据：模拟详情 RuntimeError 后直接得到 {}；方法内没有日志或诊断结果。
- 影响：搜索仍表现为成功，但演职员、别名、外部 ID 等缺失，无从判断是服务没有数据、限流、网络故障还是程序 bug。
- 建议：允许基础候选降级，但附带“详情获取失败”的受控诊断；预期网络错误分类，非预期程序错误保留内部异常栈。V4 认证回退记录实际原因和最终认证渠道，不泄漏查询 API Key。
- 验收：详情失败不阻断基础搜索，页面/日志能解释信息缺失；限流、鉴权、解析错误与编程异常可区分；正常没有详情不记误导错误。

### R31：llm.log 有设施，没有调用记录

- 位置：`backend/app/core/logger.py:144`；`service/ai_provider.py:73`、`:114`；`ai_parse_service.py:100`。
- 原因：get_llm_logger 在 app 代码中只有定义，没有调用方；AI 调用仅返回耗时/usage，未在专用日志记录调用结果、模型、任务关联及错误分类。
- 影响：用户反映 AI 连接/解析失败时，llm.log 无法追溯对应调用；启动日志存在不代表调用日志完整。
- 建议：在统一 AI 调用边界记录开始/结束摘要，绑定任务/条目/用户或请求标识，保留模型、次数、耗时、HTTP 分类和 usage；成本未知不伪造估算，不记录完整 prompt、响应正文、文件路径或凭据。
- 验收：测试连接、解析成功、鉴权失败、超时、无效内容都有可关联记录；拦截未外发应记录 skipped/blocked 而不是伪造调用；日志写入失败遵循 R27。

### R32：远端内容错误未统一转换

- 位置：`backend/app/service/shared_protocols/webdav.py:83`、`:105`；`service/ai_provider.py:143`、`:155`。
- 原因：WebDAV XML 解析在请求 try 之外，ET.ParseError 不是路由捕获的 ValueError；AI decode 的 UnicodeDecodeError 不在 provider 的失败转换列表中。
- 证据：模拟非合法 XML 抛 ET.ParseError；模拟 AI 200 响应含非 UTF-8 字节抛 UnicodeDecodeError，没有得到 failed 结果。
- 影响：反向代理返回 HTML、乱码、损坏内容等现实场景变成泛化 500；无法说明远端响应格式不合法。连接和业务状态可能不一致。
- 建议：解析与结构校验纳入外部响应错误类型；客户端安全说明“服务响应格式无效”，内部记录来源、状态、长度和异常链，不打印整段远端正文。与响应大小预算一起处理。
- 验收：HTML/XML/JSON 格式错误、非 UTF-8、空 body、异常字段类型均给出分类失败；程序错误不混成鉴权/网络失败。

### R33：路径形式中的密码没有被脱敏

- 位置：`backend/app/service/shared_protocols/webdav.py:25-36`；`media_source_service.py:437`、`:490`；`audit_service.py:66-83`。
- 原因：规范化保留 URL netloc 的 userinfo，连接测试把完整 path 写入 batch 日志；审计仅按字段名脱敏，不检查 path 内的用户名/密码。
- 证据：只使用 https://review:synthetic-secret@review.invalid/dav/ 和模拟协议；秘密出现在规范化结果、审计 path 和 logger 调用参数中。没有访问该地址。
- 影响：用户把凭据放进 URL 时，凭据可能出现在日志、审计和页面路径中，日志导出扩大泄露面。与 R08 跨源发送认证是不同问题。
- 建议：URL 配置拒绝 userinfo，用户名/密码只用独立凭据字段；统一 URL/异常字符串脱敏，处理历史记录及导出。避免仅针对 password 键做遮盖。
- 验收：URL 内嵌凭据被明确拒绝；虚构秘密不出现在新日志、审计、API 返回和导出；已有记录清理/迁移不破坏业务关联。

### R34：连通不等于具有目录访问能力

- 位置：`backend/app/service/shared_protocols/webdav.py:211-221`。
- 原因：OPTIONS 返回 2xx/3xx 即 success=true/readable=true，没有验证 PROPFIND、根 collection、认证与目录访问权限。
- 证据：模拟 OPTIONS 200，连接测试显示可读；同一模拟服务 PROPFIND 返回无效内容，目录浏览直接失败。
- 影响：代理/普通站点能响应 OPTIONS 也被当作 WebDAV 可读，用户配置成功后才发现不能使用。
- 建议：分层报告网络/TLS、认证、WebDAV 目录读取；以只读 PROPFIND 验证根路径，不在连接测试偷偷创建/移动文件来证明写能力。writable 未验证时保持未知。
- 验收：OPTIONS 200 但非 DAV、PROPFIND 403、普通文件路径、合法空目录各有准确结果和建议；无真实写入副作用。
